gp_to_parquet.py — выгрузка таблицы Greenplum в parquet
========================================================

Файл скрипта: /home/имя_папки_проекта/gp_to_parquet.py

Скрипт читает таблицу Greenplum и сохраняет данные в parquet-файлы:
по одному файлу на каждое значение ключевого поля. Имя файла:

    exp_<schema>_<table>_<key_value>.parquet

Пример: ключ rrr_id со значением 444 -> exp_schema_tbl_444.parquet

После каждой выгрузки в каталоге скрипта дописывается отчёт parq_resume.txt:
когда запускали, по какой таблице/ключу, сколько строк выгрузили, какие файлы
получились — или текст ошибки, если что-то пошло не так.


ПОЧЕМУ НЕ PYARROW
-----------------
pyarrow в этом окружении поставить нельзя — ограничение тз. Поэтому схема такая:

  * забор данных — psycopg2 + серверный COPY (SELECT ...) TO STDOUT WITH CSV
    (Greenplum сам сериализует, Python не разбирает строки построчно);
  * CSV -> Parquet — DuckDB (нативный векторный движок, пишет потоково,
    без загрузки в память, сжатие zstd);
  * типы колонок берутся из каталога (pg_attribute + format_type) и явно
    передаются в DuckDB, чтобы не терять uuid, numeric, timestamp, boolean и т.д.

Замер на тестовой БД: 1,35 млн строк (386 МБ CSV) -> parquet за 1,3 с.
Узкое место — канал до GP (~1,5 МБ/с), поэтому параллельные воркеры дают
основной выигрыш (в тесте 4 воркера — примерно в 5 раз быстрее
последовательного запуска).


ЗАПУСК
------
    cd /home/имя_папки_проекта

    # всё, по файлу на каждый src_id (ровно исходный пример)
    ./gp_to_parquet.py exp_schema tbl src_id all

    # по 1000 строк на файл, 4 потока
    ./gp_to_parquet.py exp_schema tbl src_id 1000 --workers 4

    # посмотреть план, ничего не выгружая
    ./gp_to_parquet.py exp_schema tbl src_id all --dry-run

Результат по умолчанию пишется в каталог скрипта:

    exp_schema_tbl_111.parquet
    exp_schema_tbl_444.parquet
    exp_schema_tbl_777.parquet
    ...


ПАРАМЕТРЫ
---------
  schema table key limit   позиционные: схема, таблица, ключ, all или число
  --limit                  максимум строк НА КАЖДЫЙ файл (не на всю выгрузку)
  --where                  доп. условие SQL, например "deleted_ind = 0"
  --columns                выгрузить только часть колонок
  --order-by               сортировка внутри файла
  --workers                параллельные потоки (0 = авто, но не больше
                           свободных соединений роли)
  --compression            zstd (по умолчанию), snappy, gzip, brotli, lz4,
                           uncompressed
  --compression-level      уровень сжатия (по умолчанию 3 для zstd)
  --row-group-size         размер row group в строках (по умолчанию 250000)
  --threads-per-worker     потоков DuckDB на воркер (0 = авто)
  --retries                повторов при ошибке выгрузки файла (по умолчанию 1)
  --max-files              предохранитель от слишком большого числа файлов
                           (по умолчанию 10000, 0 — без ограничения)
  --overwrite              перезаписать существующие файлы
  --dry-run                показать план и выйти
  --output-dir             каталог для parquet (по умолчанию каталог скрипта)
  --temp-dir               каталог для временных CSV
  --env-file               файл с параметрами подключения
  --resume-file            файл-отчёт о выгрузке
                           (по умолчанию <каталог скрипта>/parq_resume.txt)
  --keep-temp              не удалять временные CSV
  --quiet                  только итог


ФАЙЛ-ОТЧЁТ parq_resume.txt
---------------------------
Создаётся в каталоге скрипта (рядом с gp_to_parquet.py) после каждой выгрузки.
Записи дописываются блоками, т.е. в файле хранится история всех запусков.
Для каждого запуска фиксируется:

  * дата/время запуска и завершения;
  * команда, таблица, ключ, лимит, выходной каталог;
  * статус: УСПЕШНО / ОШИБКА / ОШИБКА (частично) / НЕТ ДАННЫХ / ОТМЕНЕНО;
  * сколько файлов сделано, сколько пропущено, сколько с ошибками;
  * сколько строк выгружено и общий объём;
  * длительность;
  * список файлов с числом строк и размером;
  * текст ошибки (общей или по конкретному ключу), если что-то пошло не так.

Пример блока:

  ================================================================================
  Запуск:       2026-10-30 11:48:02
  Завершение:   2026-10-30 11:48:23
  Команда:      ./gp_to_parquet.py exp_schema tbl rrr_id 5
  Таблица:      exp_schema.tbl
  Ключ:         rrr_id
  Лимит:        5 (на файл)
  Каталог:      /home/имя_папки_проекта
  Статус:       УСПЕШНО
  Файлов:       5 (пропущено: 0, ошибок: 0)
  Строк:        13
  Объём:        12.5 KB
  Длительность: 21.1 c

  Файлы:
    exp_schema_tbl_111.parquet: 5 строк, 3.3 KB, 0.7 c
    ...

При --dry-run отчёт не пишется (выгрузки не было). Путь можно изменить
параметром --resume-file.


ДОПОЛНИТЕЛЬНО
-------------
  * докачка: существующий parquet пропускается, только если число строк
    в нём совпадает с ожидаемым (защита от файла, сделанного с другим
    --limit);
  * имена файлов санитизируются (NULL, EMPTY, кириллица/пробелы -> "_"),
    коллизии разводятся суффиксом _2;
  * соединения переиспользуются потоком-воркером (5 ключей — 1 коннект,
    а не 5);
  * учёт rolconnlimit: на UAT у роли лимит 7 соединений, авто-режим сам
    снижает число воркеров;
  * ретраи на сетевых сбоях, атомарная запись через .tmp, Ctrl+C отменяет
    активные COPY;
  * временные CSV кладутся в /tmp/.private/<user>/user_project и удаляются
    (.sql в проекте не создаются).


ПОДКЛЮЧЕНИЕ
-----------
Параметры берутся из .env.secret_db рядом со скриптом (или из --env-file):

    GP_OUT_HOST
    GP_OUT_PORT
    GP_OUT_DB
    GP_OUT_USER
    GP_OUT_PASSWORD
    GP_OUT_SSLMODE        (опционально, по умолчанию prefer)
    GP_OUT_GSSENCMODE     (опционально, по умолчанию disable)
    GP_OUT_CONNECT_TIMEOUT (опционально, по умолчанию 30)


ПРОВЕРЕНО НА РЕАЛЬНЫХ ДАННЫХ
----------------------------
exp_schema.tbl, ключ src_id — 5 значений, 1 370 732 строки.
Контрольная сверка по src_id = 438 (21 702 строки): count, count(distinct),
суммы, min/max timestamp, длина текста и число NULL — полностью совпали
с БД.

Нюансы Greenplum, которые пришлось учесть:
  * обязателен gssencmode=disable (иначе "invalid response to GSSAPI
    negotiation");
  * GP 5.28 не понимает новый синтаксис COPY ... WITH (FORMAT csv) —
    используется старый WITH CSV NULL AS '\N'.


================================================================================
gp_from_parquet.py — загрузка parquet в Greenplum
================================================================================

Файл скрипта: /home/имя_папки_проекта/gp_from_parquet.py

Читает один parquet-файл или все файлы по маске, при необходимости фильтрует
и сортирует данные, затем грузит их в таблицу Greenplum через
COPY ... FROM STDIN порциями (после каждой порции — COMMIT).


ЗАПУСК
------
    cd /home/имя_папки_проекта

    # один файл
    ./gp_from_parquet.py exp_schema_tbl_111.parquet exp_schema tbl

    # все файлы по маске, сортировка, батч 50 000 строк
    ./gp_from_parquet.py "exp_schema_tbl_*.parquet" exp_schema tbl 50000 \
        --order-by ctrr_key

    # с фильтром
    ./gp_from_parquet.py "exp_*.parquet" exp_schema tbl 10000 \
        --where "rrrr_name='7777777777'"

    # посмотреть план, ничего не загружая
    ./gp_from_parquet.py "exp_*.parquet" exp_schema tbl --dry-run

    # то же самое в форме key=value
    ./gp_from_parquet.py source="exp_*.parquet" schema=exp_schema table=tbl \
        batch_size=10000 order_by=ctrr_key where="rrrr_name='7777777777'"


ПАРАМЕТРЫ
---------
  source                   имя parquet-файла или маска (exp_*.parquet)
  schema                   схема таблицы назначения
  table                    таблица назначения
  batch_size               строк в одной порции (COMMIT после каждой),
                           по умолчанию 10000
  --order-by               поле(я) сортировки перед вставкой, например
                           "rrrr_key" или "rrr_id, rrrr_key"; пусто — не сортировать
  --where                  условие фильтрации (SQL DuckDB), например
                           "rrrr_name='7777777777'"
  --limit                  загрузить не более N строк (для проверки)
  --truncate               очистить таблицу назначения перед загрузкой
  --dry-run                показать план и выйти
  --synchronous-commit     on|off, по умолчанию off (быстрее; при падении
                           сервера последние коммиты могут потеряться)
  --env-file               файл с параметрами подключения
  --resume-file            файл-отчёт (по умолчанию <каталог скрипта>/parq_exp_resume.txt)
  --temp-dir               каталог для временных CSV
  --keep-temp              не удалять временный CSV
  --quiet                  только итог

  Любой параметр можно задать и в форме key=value: source=..., schema=...,
  table=..., batch_size=..., order_by=..., where=..., limit=...
  (порядок не важен; --truncate, --dry-run и прочие флаги — как обычно).


КАК ЭТО РАБОТАЕТ
----------------
  1. DuckDB читает parquet (маска раскрывается скриптом), применяет WHERE
     и сортировку и один раз материализует результат во временную таблицу
     с номером строки __rn — дальше нарезка на порции идёт без повторной
     сортировки и без медленного OFFSET.
  2. Каждая порция выгружается DuckDB в CSV (нативный быстрый writer)
     и сразу заливается в Greenplum через COPY ... FROM STDIN WITH CSV —
     самый быстрый штатный способ вставки.
  3. После каждой порции выполняется COMMIT (размер порции = batch_size).
  4. По окончании в каталог скрипта дописывается отчёт parq_exp_resume.txt.

Колонки parquet сопоставляются с колонками таблицы по имени (без учёта
регистра). Если в parquet есть колонка, которой нет в таблице — скрипт
остановится с понятной ошибкой. Если в таблице есть колонки, которых нет
в parquet, они получают значения по умолчанию / NULL.


ФАЙЛ-ОТЧЁТ parq_exp_resume.txt
------------------------------
Создаётся в каталоге скрипта, записи дописываются блоками (история запусков).
Для каждого запуска фиксируется:

  * дата/время запуска и завершения;
  * команда, источник, число файлов, таблица, размер батча;
  * условия сортировки и фильтрации;
  * статус: УСПЕШНО / ОШИБКА / НЕТ ДАННЫХ / ОТМЕНЕНО;
  * сколько строк загружено и сколько было в источнике;
  * сколько батчей выполнено;
  * время выполнения, время загрузки (COPY+COMMIT), время подготовки;
  * список файлов;
  * текст ошибки, если что-то пошло не так.

Пример блока:

  ================================================================================
  Запуск:           2026-10-30 12:23:05
  Завершение:       2026-10-30 12:23:56
  Команда:          ./gp_from_parquet.py exp_..._444.parquet wrk_san t 5000 --order-by rrrr_key
  Источник:         exp_schema_tbl_444.parquet
  Файлов:           1
  Таблица:          wrk_san.gp_from_parquet_test
  Размер батча:     5 000
  Сортировка:       rrrr_key
  Фильтр:           нет
  Статус:           УСПЕШНО
  Строк загружено:  21 702
  Батчей:           5 из 5
  Время выполнения: 50.9 c
  Время загрузки:   28.8 c
  Подготовка:       0.0 c

  Файлы:
    exp_schema_tbl_444.parquet (916.2 KB)


ЗАМЕЧАНИЯ
---------
  * --where и --order-by — это SQL-выражения для DuckDB. Если колонка
    строковая, значение надо брать в кавычки: --where "rrrr_name='777...'".
    На попытку сравнить varchar с числом скрипт выведет подсказку.
  * --truncate выполняется до загрузки и фиксируется сразу: если загрузка
    потом упадёт, таблица останется с частичными данными (уже загруженные
    батчи закоммичены).
  * Отчёт пишется и при успехе, и при ошибке. При --dry-run не пишется.
